# Accessibility — WCAG 2.2 AA, in audit order

AA is the target. It is what EN 301 549 wraps, what the European Accessibility
Act has required of consumer-facing e-commerce, banking, transport and e-books
since **28 June 2025**, and what US courts read ADA Title III against.

Audit in this order. It is roughly cheapest-to-fix first, and the early items
are the ones that block a keyboard or screen-reader user entirely.

## 1. The consent banner

Audit it before the app. It is modal, it is first, and every visitor meets it.

- [ ] Reachable by keyboard with no pointer, and it receives focus when it opens
- [ ] `Esc` dismisses it; focus returns to where it was
- [ ] No keyboard trap — `Tab` cycles inside a modal, or escapes a non-modal
      (SC 2.1.2)
- [ ] It does not hide the element that currently has focus (**SC 2.4.11 Focus
      Not Obscured**, new in 2.2 — a sticky bottom banner over a focused
      footer link is the textbook failure)
- [ ] Buttons ≥ 24×24 CSS px, or spaced to compensate (**SC 2.5.8**, new in 2.2)
- [ ] Text contrast ≥ 4.5:1; button borders and focus ring ≥ 3:1 (SC 1.4.3,
      1.4.11)
- [ ] Accept and Reject have equal visual weight — a low-contrast Reject fails
      1.4.3 *and* invalidates consent under the EDPB Taskforce findings
- [ ] Marked up as a dialog: `role="dialog"`, `aria-modal="true"`,
      `aria-labelledby` pointing at its heading — or, if non-modal, placed early
      in DOM order so it is reachable without hunting
- [ ] Content behind it is inert while it is open (`inert`, not just a z-index)
- [ ] It does not reflow or resize the page under the user on dismiss

## 2. Keyboard and focus, app-wide

- [ ] Every interactive element is reachable and operable by keyboard (SC 2.1.1)
- [ ] Focus is always visible, with a ≥ 3:1 indicator (SC 2.4.7, 1.4.11).
      `outline: none` with no replacement is the single most common AA failure
- [ ] Focus order follows the visual order (SC 2.4.3)
- [ ] A skip link to main content, first in the tab order (SC 2.4.1)
- [ ] Dropdowns, menus and custom widgets respond to arrows, `Enter`, `Esc`
- [ ] Nothing is pointer-only: no hover-only reveal, no drag without a
      single-pointer alternative (SC 2.5.7, new in 2.2)

## 3. Structure and semantics

- [ ] One `<h1>` per page, headings in order, no level skipped (SC 1.3.1)
- [ ] Landmarks: `<header> <nav> <main> <footer>`, one `<main>`
- [ ] Lists are lists, tables are tables with `<th scope>`, buttons are
      `<button>` and links are `<a>` — a clickable `<div>` fails 4.1.2
- [ ] `<html lang>` set (SC 3.1.1)
- [ ] Every page has a unique, descriptive `<title>` (SC 2.4.2)
- [ ] Link text makes sense alone — no bare "click here", "read more" (SC 2.4.4)

## 4. Content

- [ ] Meaningful images have `alt`; decorative ones have `alt=""` (SC 1.1.1)
- [ ] Icon-only buttons have an accessible name (`aria-label` or visually
      hidden text)
- [ ] Colour is never the only carrier of meaning (SC 1.4.1)
- [ ] Text over images meets contrast against the worst region behind it
- [ ] Video has captions; audio has a transcript (SC 1.2.2, 1.2.1)
- [ ] Nothing flashes more than three times per second (SC 2.3.1)
- [ ] Motion respects `prefers-reduced-motion`; anything auto-playing over five
      seconds can be paused (SC 2.2.2)

## 5. Forms

- [ ] Every input has a `<label>`, programmatically associated (SC 3.3.2)
- [ ] Errors are identified in text, not by colour or position alone (SC 3.3.1)
- [ ] Error messages say how to fix it (SC 3.3.3)
- [ ] Errors are announced — `aria-live`, or move focus to the summary
- [ ] `autocomplete` on identity fields (SC 1.3.5)
- [ ] Nothing already provided is asked for twice in one process (**SC 3.3.7
      Redundant Entry**, new in 2.2)
- [ ] Authentication has a route that does not depend on memory or puzzle-solving
      — password managers and paste must work (**SC 3.3.8 Accessible
      Authentication**, new in 2.2)

## 6. Responsive and zoom

- [ ] Usable at 320 px wide with no horizontal scroll (SC 1.4.10 Reflow)
- [ ] Usable at 200% zoom (SC 1.4.4)
- [ ] Text spacing can be overridden without clipping (SC 1.4.12)
- [ ] Works in both orientations (SC 1.3.4)
- [ ] Help mechanisms stay in the same relative place across pages (SC 3.2.6,
      new in 2.2)

## What to run

Automated tools find roughly a third of AA issues. They are the start, never the
audit.

```bash
npx @axe-core/cli http://localhost:3000            # per URL
npx pa11y-ci --sitemap https://example.com/sitemap.xml
npx lighthouse http://localhost:3000 --only-categories=accessibility
```

For React and Next projects, `eslint-plugin-jsx-a11y` catches a class of these
at authoring time and belongs in the lint config rather than in an audit.

Then do the three manual passes no tool substitutes for:

1. **Unplug the mouse.** Complete the primary flow with `Tab`, `Enter`, arrows
   and `Esc`. Most failures show up in the first thirty seconds.
2. **Turn on a screen reader.** VoiceOver (`Cmd-F5`) on macOS, NVDA on Windows.
   Listen to the banner and the primary flow. Unlabelled controls are obvious
   the moment they are read aloud.
3. **Zoom to 200% and narrow to 320 px.** Watch for content that clips,
   overlaps, or scrolls sideways.

## The new-in-2.2 criteria, gathered

Easy to miss on a site last audited against 2.1:

| SC | Level | What it asks |
| --- | --- | --- |
| 2.4.11 Focus Not Obscured (Minimum) | AA | Focused element is not entirely hidden by sticky UI |
| 2.5.7 Dragging Movements | AA | Anything draggable has a single-pointer alternative |
| 2.5.8 Target Size (Minimum) | AA | 24×24 CSS px, or adequate spacing |
| 3.2.6 Consistent Help | A | Help sits in the same relative order on every page |
| 3.3.7 Redundant Entry | A | Do not re-ask for information already given |
| 3.3.8 Accessible Authentication (Minimum) | AA | No cognitive function test without an alternative |

WCAG 2.2 also removed 4.1.1 Parsing — duplicate IDs and unclosed tags are no
longer a conformance failure on their own, though they still break assistive
technology in practice.
